# ساخت NL2SQL امن؛ چطور اجازه ندهیم LLM دیتابیس را کنترل کند؟

دادن schema دیتابیس به یک LLM و اجرای SQL تولیدشده، ساده‌ترین demo از NL2SQL است؛ اما مدل هم می‌تواند query پرهزینه بسازد، به جدول نامربوط دست بزند یا معنای سؤال را اشتباه بفهمد. طراحی امن‌تر این است که مدل فقط اطلاعاتی را استخراج یا تصمیم‌های محدودی را پیشنهاد دهد و کد و دیتابیس مرز اجرای واقعی را enforce کنند.

در [پست کانال دربارهٔ NL2SQL](https://t.me/LLMEngineers/365) و [یادداشت فرق structured output و tool calling](https://t.me/LLMEngineers/366) این تفکیک را مطرح کردم.

## اول مشخص کنید واقعاً SQL لازم است؟

اگر قرار است از متن فاکتور تاریخ، مبلغ و شمارهٔ سفارش بیرون بیاید، این کار extraction است؛ خروجی ساختاریافته بگیرید، بعد مقدارها را validate کنید. اگر کاربر می‌پرسد کدام تیم باید یک ticket را بگیرد، شاید classification یا تصمیم‌گیری بین چند گزینه کافی باشد. NL2SQL را وقتی انتخاب کنید که سؤال واقعاً نیازمند query انعطاف‌پذیر روی داده است.

حتی در آن حالت، لازم نیست مدل همهٔ SQL را از صفر بنویسد. برای گزارش‌های پرتکرار و حساس، از query template یا query builder شروع کنید و فقط ورودی‌هایی مثل بازهٔ زمانی یا دسته را از مدل بگیرید. اگر schema یا فیلترها به‌صورت محدود و ثابت قابل تعریف‌اند، همان محدودیت را حفظ کنید.

## مسیر امن‌تر: مدل پیشنهاد می‌دهد، برنامه اجرا را کنترل می‌کند

یک pipeline کم‌ریسک می‌تواند این‌طور باشد:

۱. سؤال کاربر را به intent و پارامترهای ساختاریافته تبدیل کنید.
۲. نام فیلدها، نوع داده و مقدارها را با schema برنامه اعتبارسنجی کنید.
۳. فقط tableها و columnهای allowlistشده را در اختیار query builder بگذارید.
۴. مقدارها را به‌شکل parameterized bind کنید؛ رشتهٔ کاربر را به متن SQL نچسبانید.
۵. ساختار query را با AST parser یا policy checker بررسی کنید، ولی parser را جایگزین کنترل دسترسی دیتابیس ندانید.
۶. همان query را با نقش read-only و دسترسی به viewهای لازم اجرا کنید.
۷. برای اجرا timeout، سقف ردیف و سقف هزینه بگذارید؛ برای خروجی غیرعادی یا اقدام حساس، تأیید بگیرید.

اگر لازم است مدل SQL کامل بسازد، اجرای query را همچنان در کد محدود کنید. برای نمونه، policy می‌تواند فقط `SELECT` را بپذیرد و جدول‌ها یا functionهای خاص را رد کند. اما بررسی یک parser کافی نیست؛ دسترسی دیتابیس باید حتی در صورت bug یا bypass هم محدود بماند.

## دسترسی فقط‌خواندنی کافی نیست

حساب فقط‌خواندنی جلوی `INSERT`، `UPDATE` و `DELETE` را می‌گیرد، ولی جلوی خواندن داده‌ای را که کاربر اجازه ندارد ببیند نمی‌گیرد. credential برنامه را فقط به جدول‌ها یا viewهای لازم محدود کنید و row-level security را مطابق هویت کاربر اعمال کنید. تست کنید که کاربر tenant اول نتواند با تغییر عبارت یا prompt به ردیف tenant دوم دسترسی پیدا کند.

راهنمای OWASP می‌گوید accountهایی که فقط نیاز به خواندن دارند باید فقط همان read permission موردنیاز را بگیرند، نه دسترسی DBA. همچنین SQL Injection Prevention guidance بر bind کردن مقدارهای غیرقابل‌اعتماد و whitelist کردن identifierهای پویا تأکید می‌کند. این قواعد برای queryی که LLM پیشنهاد داده هم لازم‌اند.

## چرا LIMIT و timeout کارایی را کنترل می‌کنند، نه دسترسی را؟

شرط `LIMIT` می‌تواند تعداد ردیف خروجی را کم کند، اما لزوماً جلوی scan پرهزینه را نمی‌گیرد. `statement_timeout` یا سقف زمان معادل در database و محدودیت resource در لایهٔ سرویس لازم‌اند. query plan، حجم دادهٔ خوانده‌شده و cancel شدن درخواست را هم پایش کنید.

اگر نتیجه به فیلتر تاریخ وابسته است، مرزهای زمانی را در کد محاسبه و validate کنید. من در یکی از مثال‌های کانال از تبدیل «دو هفتهٔ آخر مرداد» به بازهٔ دقیق و بعد ساخت query در برنامه گفتم؛ اینجا مدل زبان طبیعی را به پارامتر قابل‌کنترل تبدیل می‌کند، نه این‌که مسئول نوشتن هر join و aggregate باشد.

## فرق Structured Output با Tool Calling چیست؟

در Structured Output مشخص می‌کنیم پاسخ چه schemaای داشته باشد؛ مثلاً `intent`, `from_date` و `to_date`. این کار شکل داده را کنترل می‌کند، ولی درستی semantic مقدارها را تضمین نمی‌کند. Tool Calling راهی برای درخواست اجرای action است: مدل پارامترها را می‌فرستد، برنامه آن‌ها را بررسی می‌کند، ابزار اجرا می‌شود و نتیجه به مدل برمی‌گردد.

پس اگر خروجی مدل از نظر schema معتبر است، هنوز باید بفهمیم تاریخ درست parse شده؟ کاربر اجازهٔ دیدن این داده را دارد؟ query روی دیتابیس چه اثری خواهد گذاشت؟ اعتبار ساختار با اعتبار تصمیم یکی نیست.

## چه زمانی human approval لازم است؟

برای داشبورد داخلی فقط‌خواندنی، نمایش query یا خلاصهٔ آن پیش از اجرا می‌تواند مرحلهٔ تأیید مناسبی باشد. برای queryهای حساس، دسترسی وسیع یا export انبوه، تأیید انسانی و logging دقیق لازم است. اگر اقدام از read-only خارج می‌شود، مانند تغییر داده، مسیر جدا با مجوز صریح و کنترل transactional طراحی کنید.

## جمع‌بندی

در طراحی NL2SQL، دسترسی آزاد به دیتابیس ندهید. مدل در فهم زبان طبیعی کمک می‌کند؛ برنامه سؤال را به schema و allowlist محدود می‌کند؛ و دیتابیس با role، RLS و timeout آسیب احتمالی را مهار می‌کند. اگر query را می‌شود با template و پارامتر ساخت، لازم نیست مدل SQL آزاد تولید کند.
