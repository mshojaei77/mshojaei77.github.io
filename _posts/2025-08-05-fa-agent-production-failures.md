# چرا Agentها در محیط عملیاتی شکست می‌خورند؟

یک Agent که در یک demo موفق می‌شود، هنوز ثابت نکرده در محیط واقعی قابل اتکاست. بین یک اجرای خوش‌شانس و سیستمی که برای کاربران، داده‌های ناقص و سرویس‌های گاهی‌خراب کار می‌کند فاصله هست. این فاصله را باید با failure modeها، ابزارهای قابل‌خطا، کنترل دسترسی، هزینه و معیارهای ارزیابی سنجید.

جملهٔ «اکثر Agentها شکست می‌خورند» را نباید نتیجهٔ آماری دانست، مگر این‌که جامعه، تعریف شکست و دادهٔ پشتیبان روشن باشند. برای طراحی بهتر، مهم‌تر است failureها را به شکل مشخص ببینیم و برای هرکدام کنترل داشته باشیم.

## ورودی مبهم، خروجی مبهم

اگر Agent باید «درخواست را رسیدگی کند» ولی تعریف نشود رسیدگی موفق یعنی چه، مدل ممکن است پاسخ قابل‌قبولی بنویسد اما سفارش را تغییر ندهد، درخواست ناقص را حدس بزند یا اصلاً مرحله‌ای را جا بیندازد. معیار پذیرش را قبل از پیاده‌سازی روشن کنید: چه stateی باید تغییر کند؟ چه چیزی باید بدون تغییر بماند؟ چه شرایطی باید به اپراتور ارجاع شود؟

برای taskهای مهم، چند نمونهٔ واقعی و مرزی بسازید. اگر دو نفر از تیم دربارهٔ پاس یا fail اختلاف دارند، احتمالاً spec یا grader هنوز به‌اندازهٔ کافی روشن نیست.

## ابزارها در دنیای واقعی خطا می‌دهند

یک سرویس API ممکن است timeout شود، rate limit بدهد یا پاسخ ناقص برگرداند. مدل هم ممکن است پارامتر نامعتبر بسازد یا همان درخواست را چند بار تکرار کند. به هر ابزار timeout و schema اعتبارسنجی‌شده بدهید. retry باید محدود و فقط برای خطاهای گذرا باشد؛ تکرار یک عملیات غیر idempotent مثل پرداخت یا ثبت سفارش می‌تواند اثر جانبی را دو بار اعمال کند.

اگر سیستم پس از timeout نمی‌داند درخواست قبلی انجام شده یا نه، کورکورانه دوباره اجرا نکند. از idempotency key، خواندن state قبل از اقدام بعدی یا صفی با تضمین‌های مناسب استفاده کنید.

## نبود state و context گمراه‌کننده

کار طولانی ممکن است از چندین فراخوانی یا session بگذرد. اگر پیشرفت فقط در history مدل باشد، فشرده‌سازی، restart یا انتقال کار می‌تواند تصمیم‌ها و شواهد را حذف کند. state عملیاتی را بیرون از context ثبت کنید: چه کاری کامل شده، چه چیزی هنوز تأیید نشده، کدام مدرک منبع دارد و قدم بعدی مجاز چیست.

از طرف دیگر، هرچه را در اختیار Agent هست وارد prompt نکنید. context قدیمی، متناقض یا نامرتبط می‌تواند تصمیم را بدتر کند. بازیابی، خلاصه‌سازی و تفویض به sub-agent هم اطلاعاتی را حذف می‌کنند؛ باید امکان دیدن منبع و بازیابی مدرک مهم باقی بماند.

## حلقهٔ ادامه پیدا می‌کند یا زود موفقیت اعلام می‌کند

یک حلقهٔ Agent به شرط پایان نیاز دارد: پاسخ معتبر، وضعیت نهایی محیط یا رسیدن به سقف تلاش. بدون سقف، سیستم می‌تواند ابزار را پشت‌سرهم صدا بزند و هزینه را بالا ببرد. سقف سخت هم به‌تنهایی کافی نیست؛ وقتی تمام شد، Agent باید نتیجهٔ ناقص را گزارش کند یا کار را ارجاع دهد، نه این‌که موفقیت بسازد.

برای کارهای دارای اثر جانبی، انجام واقعی را از متن پاسخ جدا کنید. تأیید رزرو را از پایگاه داده یا سرویس رزرو بخوانید؛ ادعای مدل دربارهٔ رزروشدن مدرک نیست.

## دسترسی بیش از حد

اگر Agent فقط لازم دارد چند فایل را بخواند، دادن دسترسی کامل به دیسک، شبکه و credentialهای تولیدی دامنهٔ خطا را بزرگ می‌کند. اصل حداقل دسترسی را در ابزار و محیط اجرا enforce کنید. عملیات حساس را با مجوز انسانی یا rule قطعی محافظت کنید. prompt می‌تواند رفتار مطلوب را توضیح دهد، ولی sandbox و کنترل دسترسی باید مانع واقعی باشند.

## پایش بدون ارزیابی کافی

لاگ ساده‌ای که فقط درخواست کاربر و پاسخ نهایی را نگه می‌دارد، برای فهمیدن علت شکست کافی نیست. برای هر اجرا، نسخهٔ prompt و مدل، ابزار فراخوانی‌شده، ورودی و خروجی کنترل‌شدهٔ ابزار، زمان، retry و outcome را ثبت کنید؛ اطلاعات حساس را هم طبق سیاست نگه‌داری حذف یا ماسک کنید.

بعد از آن، traceها را به eval تبدیل کنید. راهنمای Anthropic می‌گوید transcript اجرا و outcome محیط را جدا ارزیابی کنید؛ Agent ممکن است بگوید کاری انجام شده، درحالی‌که state واقعی تغییر نکرده است. از taskهای موفق، failureهای تولید و نمونه‌های منفی مجموعهٔ آزمون بسازید. هر تغییر در prompt، مدل یا tool باید روی همان مجموعه با نسخهٔ قبلی مقایسه شود.

## یک مسیر عملی برای کاهش ریسک

۱. وظیفه را به خروجی قابل‌مشاهده و شرط توقف تبدیل کنید.
۲. مسیر قطعی را با کد نگه دارید و اختیار Agent را به انتخاب‌هایی محدود کنید که واقعاً به مدل نیاز دارند.
۳. ابزارها را با schema، timeout، مجوز و قرارداد idempotency تعریف کنید.
۴. برای پیشرفت کار state پایدار، trace قابل‌دیباگ و evalهای برگرفته از failure بسازید.
۵. ابتدا در sandbox و با کارهای کم‌ریسک اجرا کنید؛ دسترسی بیرونی را بعد از بررسی تدریجی باز کنید.

این کارها شکست را صفر نمی‌کنند. هدف این است که خطا قابل‌تشخیص، محدود و قابل‌بازیابی باشد و سیستم به‌جای ساختن پاسخ مطمئن‌نما، بتواند متوقف شود.

## جمع‌بندی

در Production، Agent با خطای API، تکرار، state ناقص، context بد و دسترسی ناامن روبه‌رو می‌شود. راه‌حل یک prompt طولانی‌تر یا framework تازه‌تر نیست؛ قرارداد روشن، ابزار قابل‌کنترل، state پایدار، ارزیابی بر مبنای outcome و مسیر توقف انسانی است. اگر هنوز نمی‌توانید بفهمید Agent چرا کاری را انجام داده، هنوز آماده نیستید اختیار بیشتری به آن بدهید.
