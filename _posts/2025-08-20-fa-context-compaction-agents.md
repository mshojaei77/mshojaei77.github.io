# فشرده‌سازی Context برای Agentهای طولانی؛ خلاصه‌سازی کافی نیست

وقتی گفت‌وگوی Agent طولانی می‌شود، پاک‌کردن چند پیام قدیمی و گذاشتن یک خلاصه معمولاً اطلاعات لازم برای ادامه را حفظ نمی‌کند. Context Compaction باید context فعال را کوچک کند، اما state مهم کار را با دقت نگه دارد یا به منبعی قابل‌بازیابی وصل کند.

پنجرهٔ context حافظهٔ کاری مدل است، نه حافظهٔ کامل سامانه. این تفاوت برای Agentهایی که چند ساعت یا چند روز کار می‌کنند مهم می‌شود؛ وضعیت پایدار باید جداگانه ذخیره و در شروع هر گام لازم، دوباره به context اضافه شود.

## خلاصه با state یکی نیست

خلاصه معمولاً روایت فشرده‌ای از مکالمه است. state جواب چند سؤال عملی را می‌دهد: هدف فعلی چیست؟ کدام مرحله کامل شده؟ چه مدرکی نتیجه را پشتیبانی می‌کند؟ چه کاری هنوز انجام نشده؟ کدام اقدام به تأیید نیاز دارد؟

اگر Agent برای خرید بلیط کار می‌کند، جملهٔ «گزینه‌ای پیدا شد و کاربر تأیید کرد» کافی نیست. باید شناسهٔ رزرو، مبلغ، تاریخ، مبدا و مقصد، منبع قیمت و این‌که پرداخت واقعاً انجام شده یا نه، ساختاریافته بماند. عدد و شناسه را به عبارت مبهم تبدیل نکنید؛ اگر منبع اصلی بیرون از context است، نشانی و نسخهٔ آن را نگه دارید.

## یک چرخهٔ compaction قابل‌بازیابی

یک فرایند compaction قابل‌بررسی می‌تواند چند مرحله داشته باشد:

۱. خروجی بزرگ ابزار را از پیام‌های رفت‌وبرگشت بیرون ببرید و در فایل، پایگاه داده یا store مناسب ذخیره کنید.
۲. پیام‌های تکراری و اطلاعات منقضی را حذف کنید؛ اما دستور اصلی کاربر، محدودیت‌ها و شواهد هنوز لازم را حفظ کنید.
۳. یک state کوتاه بسازید: هدف، پیشرفت، تصمیم‌ها و دلیلشان، شناسه‌ها، کارهای باز و قدم بعدی.
۴. منبع جزئیات را کنار state نگه دارید تا Agent بتواند در صورت نیاز برگردد و بخواند.
۵. پیش از ادامه، خروجی را از نظر توکن، صحت فیلدهای کلیدی، تناقض، سطح دسترسی و دادهٔ حساس اعتبارسنجی کنید.

این شبیه checkpoint گرفتن است، نه صرفاً نوشتن recap. نسخهٔ فشرده باید ادامهٔ کار را ممکن کند و مسیر بازگشت به evidence را از بین نبرد.

## فشرده‌سازی چه چیزی را حل نمی‌کند؟

فشرده‌سازی تضمین نمی‌کند مدل هر نکتهٔ لازم را به یاد بیاورد. خود مرحلهٔ خلاصه‌سازی ممکن است یک استثنا، شرط دسترسی یا تفاوت میان «انجام شد» و «درخواست شد» را حذف کند. حتی مقالهٔ [Context Compaction Theory](https://arxiv.org/abs/2608.01326) compaction را به مسئلهٔ انتخاب اطلاعات یا ساخت پیام فشرده صورت‌بندی می‌کند؛ در هر دو حالت، هدف نگه‌داشتن اطلاعات کافی برای پرسش‌های بعدی است، نه حفظ بی‌نقص تاریخچه.

برای همین، بخش‌هایی از state که خطا در آن‌ها هزینهٔ بالا دارد بهتر است ساختاریافته و ماشینی اعتبارسنجی شوند. خلاصهٔ زبانی برای پیوستگی مفید است؛ جای دیتابیس سفارش، journal تغییرات یا سند مرجع را نمی‌گیرد.

## قابلیت APIها با طراحی خودتان فرق دارد

در زمان نگارش این نسخه، APIهای ارائه‌دهندگان هم قابلیت compaction دارند. در Responses API از OpenAI می‌توان فشرده‌سازی server-side را با آستانه فعال کرد یا به‌صورت صریح درخواستش داد. مستندات Claude API گزینه‌هایی مثل compact on demand و compaction در آستانه را توضیح می‌دهد. جزئیات این endpointها، شکل state برگشتی و نحوهٔ ادامهٔ conversation اختصاصی همان سرویس و در حال تغییر است.

قابلیت provider مدیریت اندازهٔ context را آسان می‌کند، اما جای طراحی state اپلیکیشن را نمی‌گیرد. اگر business state، دسترسی‌ها یا اثرهای جانبی فقط داخل یک خلاصهٔ opaque نگه‌داری شوند، ممکن است برای audit و recovery کافی نباشند. این دو لایه را جدا ارزیابی کنید: آیا API می‌تواند context را جمع کند؟ آیا محصول هنوز می‌تواند وضعیت واقعی کار را بازسازی کند؟

## چطور کیفیت compaction را بسنجیم؟

چند اجرای طولانی و نماینده بسازید و پیش و پس از compaction بررسی کنید که آیا Agent قادر است کار را از همان نقطه ادامه دهد: شناسه‌ها درست مانده‌اند؟ شرط‌های کاربر حفظ شده‌اند؟ مدرک تصمیم پیدا می‌شود؟ سیستم می‌داند چه اقدامی نیازمند اجازه است؟ این آزمون‌ها را به چند سؤال ساده محدود نکنید؛ ادامهٔ task و state نهایی محیط را هم بسنجید.

همچنین دادهٔ حساس و متن‌های غیرقابل‌اعتماد را جدا نگه دارید. فشرده‌سازی نباید منشأ دستور را حذف کند و باعث شود متن استخراج‌شده از سند با سیاست توسعه‌دهنده اشتباه گرفته شود. دسترسی به فایل‌هایی که Agent بعداً برای بازیابی می‌خواند هم باید همان کنترل‌های امنیتی را رعایت کند.

## جمع‌بندی

فشرده‌سازی راهی برای سبک‌کردن context فعال است، نه حافظه‌سازی جادویی. خروجی‌های حجیم را بیرون ببرید، state حیاتی را دقیق ثبت کنید، خلاصه را به منابع قابل‌بازیابی وصل کنید و ادامهٔ کار را با آزمون واقعی اعتبارسنجی کنید. هرچه هزینهٔ فراموشی بیشتر باشد، کمتر باید به یک خلاصهٔ آزاد و غیرقابل‌ممیزی تکیه کرد.
