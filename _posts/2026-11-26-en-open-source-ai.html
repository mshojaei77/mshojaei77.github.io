What Makes an AI Model Open Source?

People use “open” to describe model weights, code, datasets, APIs, and products. Those are different kinds of access. A downloadable checkpoint may be useful for local inference or fine-tuning, but weights alone do not answer whether a system meets an open-source definition.

This guide uses the Open Source Initiative’s Open Source AI Definition (OSAID) 1.0 as a specific reference point. The definition applies the freedoms to use, study, modify, and share an AI system, and asks whether people can access the preferred form for making modifications. The name of a model or its repository label is not enough; inspect the artifacts and terms that accompany the exact version.

Start with the four freedoms

OSI’s definition asks whether people can:

  • Use the system for any purpose without asking permission.
  • Study how it works and how its results were created.
  • Modify it, including to change its behavior or outputs.
  • Share the system, with or without changes, for any purpose.

For machine-learning systems, exercising those freedoms requires more than a user-facing application or an inference endpoint. The definition names three central parts of the preferred form for modification: detailed information about training data, the code used to prepare data and build and run the system, and model parameters such as weights. The relevant code includes training and inference code, data processing and filtering, architecture, and supporting settings.

Inspect each artifact separately

ArtifactWhat to check
ParametersAre the weights and related settings available under terms that allow use, study, modification, and sharing?
CodeCan you inspect and change the code needed to process data, train the model, validate it, and run inference? Is that code under an OSI-approved license?
Data informationCan a skilled person understand the sources, collection, processing, and characteristics of the training data, and build a substantially equivalent system?
Terms for the whole releaseDo the terms for the components and their combination preserve the freedoms to use, study, modify, and share?

OSAID 1.0 does not require every raw training record to be republished. Its FAQ distinguishes data that can be shared, data that is public or obtainable elsewhere, and data that cannot be shared for reasons such as privacy or other legal constraints. For every category, the data information must describe the data's scope and characteristics, where and how it was obtained, how it was selected and processed, any labeling procedures, and what filtering was applied, with enough detail for a skilled person to build a substantially equivalent system. A source and access route are parts of that record, not a substitute for it. For unshareable data, the description must explain relevant characteristics without exposing the records themselves. A model card or short dataset summary by itself may not provide the information the definition calls for.

Open weights are not the whole test

“Open weights” describes access to learned parameters. OSAID applies the same preferred-form requirements when a release is described as an open-source model or open-source weights: the code and data information used to derive the parameters matter too. A checkpoint can still be useful while falling short of that definition.

Check the terms for weights and code independently. A repository can expose files while its terms limit who may use them or for which purposes. The Open Source Definition for software does not permit discrimination against people, groups, or fields of endeavor. Terms that add such restrictions should not be treated as equivalent to an OSI-approved open-source software license.

Training-data rights need their own review. A dataset’s availability does not automatically settle the rights to use, redistribute, or adapt its contents. Creative Commons provides guidance for applying CC license conditions to AI training; the relevant obligations depend on the license and the activity. Record what applies to each artifact instead of assuming one label covers the entire system.

Openness enables inspection; it does not certify quality

Access to code, parameters, and data information can make independent inspection and adaptation possible. It does not guarantee that a model is accurate, secure, unbiased, suitable for a particular task, or cheap to operate. Those questions need their own evaluations, with representative data and the deployment conditions you care about.

Likewise, openness is not a single performance level. A release can provide extensive training details and still have limited capability; another can have useful weights while withholding the preferred form for modification. Keep the questions distinct: what may users do, what can they inspect, and how well does the system perform for this application?

A practical review checklist

  1. Identify the exact model version and the files included in that release.
  2. Read the terms for parameters, source code, and datasets separately. Check both modification and redistribution.
  3. Find the data information: sources, collection and filtering methods, known exclusions, and access conditions.
  4. Check whether training, validation, and inference code plus relevant configurations are available in a modifiable form.
  5. Evaluate capability, safety, privacy, latency, and operating cost separately for your intended use.
  6. Record the version and terms you reviewed; recheck them when the model or hosted offering changes.

The goal is a precise description, not a badge: “weights are downloadable under these terms” is a different claim from “this release meets OSAID 1.0.” State which claim your evidence supports.
