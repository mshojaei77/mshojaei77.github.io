# فرق Agent، Workflow و LLM App در کجاست؟

برای ساخت قابلیت AI لازم نیست از همان اول سراغ Agent برویم. اگر مسیر کار را می‌شود از قبل مشخص کرد، معمولاً یک workflow ساده‌تر، ارزان‌تر و قابل‌پیش‌بینی‌تر است. Agent زمانی معنا دارد که سیستم در زمان اجرا باید بر اساس نتیجهٔ قدم قبلی تصمیم بگیرد قدم بعدی چیست.

این تفکیک فقط به درست‌بودن اصطلاح‌ها مربوط نیست؛ انتخاب معماری روی تست، هزینه، امنیت و دیباگ اثر می‌گذارد.

## یک LLM App لزوماً Agent نیست

یک اپلیکیشن می‌تواند از LLM برای خلاصه‌کردن متن، استخراج چند فیلد یا نوشتن پاسخ استفاده کند، اما مسیر اجرا همچنان دست برنامه باشد. مثلاً اپلیکیشن درخواست را اعتبارسنجی می‌کند، یک بار مدل را صدا می‌زند، خروجی را با schema می‌سنجد و نتیجه را نمایش می‌دهد. این یک LLM App است؛ حضور مدل به‌تنهایی آن را Agent نمی‌کند.

در چنین طراحی‌ای، محصول تعیین می‌کند چه کاری، به چه ترتیبی و چند بار انجام شود. مدل یک مرحله از برنامه را انجام می‌دهد؛ اختیار تغییر مسیر را ندارد.

## در Workflow مسیر از قبل تعریف می‌شود

در workflow، مراحل و شرط‌های گذار را تیم طراحی می‌کند. مثلاً برای درخواست پشتیبانی: ابتدا دسته‌بندی، بعد جست‌وجوی راهنما، سپس ساخت پاسخ و در نهایت تأیید کارشناس. بخشی از این مراحل می‌تواند با LLM انجام شود، اما ترتیب و شرط‌ها همچنان در کد مشخص‌اند.

مزیتش این است که مسیرهای مهم قابل‌پیش‌بینی و تست‌پذیرند. اگر دسته‌بندی ناموفق بود، می‌توانیم طبق یک قاعدهٔ معلوم دوباره امتحان کنیم یا پرونده را به انسان بسپاریم. Workflow هم ممکن است با مدل کار کند و شرط‌های احتمالی داشته باشد؛ این ویژگی به‌تنهایی آن را به Agent تبدیل نمی‌کند.

## در Agent بخشی از مسیر حین اجرا انتخاب می‌شود

یک Agent معمولاً هدف یا مسئله‌ای می‌گیرد، محیط و نتیجهٔ ابزارها را می‌بیند و برای قدم بعدی تصمیم می‌گیرد. ممکن است جست‌وجو کند، نتیجه را بررسی کند، query دیگری بسازد یا تصمیم بگیرد پاسخ بدهد. این حلقهٔ مشاهده، اقدام و بازبینی رفتار منعطف‌تری می‌دهد؛ در عوض، تعداد مسیرهای ممکن و حالت‌های خطا بیشتر می‌شود.

هر Agent باید اختیار محدودی داشته باشد. «خودگردان» یعنی سیستم می‌تواند بعضی انتخاب‌های میان‌مرحله‌ای را انجام دهد؛ معنایش این نیست که باید هر اقدامی را بدون سقف یا اجازه اجرا کند. تعداد iteration، زمان، بودجه و ابزارهای مجاز را Harness تعیین می‌کند.

## یک مثال: بررسی درخواست بازپرداخت

فرض کنید کاربر می‌پرسد سفارش من قابل بازپرداخت است؟ اگر فقط باید شمارهٔ سفارش خوانده شود، تاریخ خرید با یک سیاست ثابت مقایسه شود و نتیجه نمایش داده شود، یک workflow مناسب است. اگر مدل فقط متن درخواست را به ساختار تبدیل کند، باز هم یک LLM App داخل workflow داریم.

اگر درخواست مبهم باشد، Agent می‌تواند سابقهٔ سفارش را ببیند، بخش مربوط از سیاست را جست‌وجو کند، اطلاعات ناقص را از کاربر بپرسد و برای مورد استثنایی پرونده را ارجاع دهد. ولی حتی اینجا هم محاسبهٔ مهلت بازگشت کالا بهتر است با کد قطعی انجام شود؛ لازم نیست مدل برای هر جمع‌وتفریق تصمیم بگیرد.

## چطور انتخاب کنیم؟

- **مسیر ثابت و معیار موفقیت روشن است؟** از کد معمولی یا workflow شروع کنید و LLM را فقط در مرحله‌ای بگذارید که فهم زبان طبیعی لازم دارد.
- **نتیجهٔ یک مرحله واقعاً مسیر بعدی را عوض می‌کند؟** اگر پاسخ بله است، یک حلقهٔ Agent محدود را بررسی کنید.
- **اقدام جانبی یا پرریسک وجود دارد؟** مجوز و تأیید را بیرون از prompt enforce کنید؛ خود مدل مرز امنیتی نیست.
- **چطور می‌فهمید سیستم موفق شده؟** خروجی نهایی و تغییر واقعی در محیط را با هم بسنجید. پیام «انجام شد» معیار کافی نیست.

راهنمای Anthropic دربارهٔ [ساخت سیستم‌های Agentic](https://www.anthropic.com/research/building-effective-agents) هم توصیه می‌کند پیچیدگی معماری با مسئله تناسب داشته باشد. شروع با workflow روشن و افزودن خودگردانی فقط جایی که لازم است، اغلب انتخاب مهندسی سالم‌تری است.

## مرزها همیشه سیاه‌وسفید نیستند

در عمل، معماری ترکیبی رایج است: workflow درخواست را می‌پذیرد، Agent فقط زیرمسئلهٔ جست‌وجو را حل می‌کند، سپس برنامه خروجی را اعتبارسنجی و ثبت می‌کند. بهتر است به‌جای بحث روی اسم، از خودمان بپرسیم چه کسی ترتیب مراحل را کنترل می‌کند، چه انتخابی به مدل سپرده شده و اگر آن انتخاب غلط بود، سیستم چطور متوقف یا اصلاح می‌شود.

نتیجه؟ برای فرایندهای ثابت، workflow؛ برای فهم یا تولید یک بخش زبانی، LLM App؛ و برای هدفی که نیاز به انتخاب چند اقدام وابسته به نتیجه دارد، Agent محدود و قابل‌ارزیابی. هر جا بتوان تصمیم را با قاعدهٔ ساده و قابل‌بررسی گرفت، همان راه معمولاً بهتر است.
