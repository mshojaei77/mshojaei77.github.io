# توسعهٔ مبتنی بر Spec؛ چطور تصمیم‌های توسعه را از تاریخچهٔ چت بیرون بیاوریم؟

اگر Coding Agent بعد از چند ساعت کار دیگر نداند کدام شرط مهم بود یا چرا یک تصمیم معماری گرفته شد، گفتن «تست‌ها سبزند» مشکل را حل نمی‌کند. یک spec پایدار می‌تواند قرارداد میان انسان و Agent باشد: چه چیزی باید ساخته شود، حدود تغییر چیست و موفقیت را با چه مدرکی می‌سنجیم.

در [پست کانال دربارهٔ workflow آزمایشی خودم](https://t.me/LLMEngineers/441) این مشکل را توضیح دادم: جزئیات قابلیت در تاریخچهٔ مکالمه گم می‌شود و build سبز به‌تنهایی درستی منطق را ثابت نمی‌کند. من آن زمان صریح گفتم که مجموعهٔ skillها روی پروژه‌های بزرگ واقعی آزمایش نشده بود؛ پس آن را تجربهٔ تولیدی جا نمی‌زنم.

## توسعهٔ مبتنی بر مشخصات یک قالب فایل واحد نیست

در Spec-Driven Development با یک خانواده از روش‌ها روبه‌رو هستیم، نه یک استاندارد با چهار فایل اجباری برای همهٔ تیم‌ها. GitHub Spec Kit نمونه‌ای از toolkitهای عمومی است؛ پروژهٔ من [sdd-agent-skills](https://github.com/mshojaei77/sdd-agent-skills) تلاش می‌کند همان ایده را در قالب skillهای قابل‌استفاده در ابزارهای Coding Agent پیاده کند. این دو را یکی نگیریم: اصول کلی را می‌توان با شکل‌های مختلف پیاده کرد.

برای یک تغییر بزرگ، چهار artifact می‌توانند کافی باشند:

- **فایل `spec.md`** مسئله، رفتار مطلوب، محدودیت‌ها و معیار پذیرش را ثبت می‌کند.
- **فایل `design.md`** انتخاب‌های معماری و اثر روی اجزای موجود را روشن می‌کند.
- **فایل `tasks.md`** کار را به گام‌های قابل‌بررسی می‌شکند.
- **فایل `verification.md`** شواهد اجرا، تست و بازبینی را نگه می‌دارد.

این‌ها نسخهٔ پیشنهادی برای workflow من‌اند، نه قانون جهانی. برای یک تغییر کوچک در متن یا اصلاح یک باگ روشن، ساختن چهار سند می‌تواند از خود کار سنگین‌تر شود.

## از درخواست تا پیاده‌سازی

**اول مسئله را دقیق کنید.** به‌جای «صفحه را بهتر کن»، نیاز را با رفتار قابل‌مشاهده بنویسید: چه کسی از کدام ورودی استفاده می‌کند، چه نتیجه‌ای می‌بیند و چه چیزی خارج از دامنه است؟ عبارت‌هایی مثل «سریع»، «امن» یا «کاربرپسند» تا وقتی معیار یا مثال نداشته باشند، برای ارزیابی مبهم‌اند.

**بعد design را با سیستم موجود تطبیق دهید.** Agent باید فایل‌ها، conventionها و معماری واقعی repository را بخواند. طراحی‌ای که فقط روی کاغذ درست است ولی با جریان فعلی data یا محدودیت سازگاری نمی‌خواند، spec خوبی نیست.

کارها را به تغییرهای قابل‌تست بشکنید. هر task باید ورودی و خروجی، وابستگی و یک روش بررسی داشته باشد. اگر task آن‌قدر بزرگ است که چند رفتار مستقل را با هم تغییر می‌دهد، failure بعدی را سخت‌تر می‌شود پیدا کرد.

**در پایان، verification را با evidence پر کنید.** کدام تست اجرا شد؟ کدام سناریو هنوز بررسی نشده؟ آیا بررسی انسانی لازم است؟ «Agent گفت درست است» evidence نیست. build و تست لازم‌اند، اما اگر spec معیار محصول را پوشش نداده باشد، سبزشدنشان فقط نشان می‌دهد پیاده‌سازی از آزمون‌های موجود گذشته است.

## کجا باید انسان وارد شود؟

این روش ابهام را حذف نمی‌کند؛ آن را زودتر آشکار می‌کند. اگر معیار پذیرش دو تفسیر معقول دارد، Agent نباید یکی را تصادفی انتخاب کند. سؤال باید پیش از پیاده‌سازی به مالک محصول یا توسعه‌دهنده برگردد. همین موضوع دربارهٔ تصمیم‌های پرریسک، مهاجرت داده، احراز هویت و تغییر API هم صدق می‌کند.

یک گام review مستقل هم مفید است: آیا spec با نیاز اصلی سازگار است؟ آیا design محدودیت امنیتی و backward compatibility را دیده؟ آیا verification واقعاً هر معیار پذیرش را می‌سنجد؟ review نباید صرفاً امضای Agent دیگری باشد؛ باید به مدرک و معیارهای روشن رجوع کند.

## هزینهٔ مستندات در برابر سربار فرایند

مستندات هم تاریخچهٔ چت را برای همیشه معتبر نمی‌کنند. اگر فایل‌ها پس از تغییر نیاز به‌روز نشوند، خودشان به منبع سردرگمی تبدیل می‌شوند. بهتر است اندازهٔ فرایند با ریسک تغییر متناسب باشد: باگ کوچک شاید فقط یک معیار و یک تست بخواهد؛ تغییر معماری می‌تواند design و چند گام بازبینی جدا لازم داشته باشد.

برای سنجیدن این workflow، یک قابلیت با محدودهٔ روشن بردارید و از ابتدا نرخ تغییرات خارج از spec، خطاهای برگشتی در review و زمان اصلاح را ثبت کنید. بعد آن را با روش معمول تیم مقایسه کنید. در پست اولیه گفتم ابزارها هنوز experimental هستند؛ تا وقتی چنین مقایسه‌ای انجام نشده، نباید ادعا کرد SDD سرعت یا کیفیت را حتماً بالا می‌برد.

## جمع‌بندی

این روش کمک می‌کند هدف، تصمیم‌های پیاده‌سازی و شواهد در فایل‌های قابل‌بازبینی بمانند؛ به‌جای این‌که فقط در context یک Agent یا تاریخچهٔ چت زندگی کنند. شروع کم‌هزینه این است: برای قابلیت‌های مهم، معیار پذیرش را قبل از کدنویسی بنویسید و بعد implementation را به همان معیارها وصل کنید. اگر مستندات با کار واقعی به‌روز نشوند یا verification ناقص باشد، فرایند صرفاً فایل‌های بیشتری تولید می‌کند.
