# مهندسی Context برای Agentها؛ فراتر از نوشتن Prompt بهتر

اگر Agent پاسخ بی‌ربط می‌دهد، همیشه مشکل از ضعیف‌بودن مدل یا بدبودن prompt نیست. شاید مدرک درست به آن نرسیده، اطلاعات قدیمی با جدید قاطی شده یا خروجی ابزار آن‌قدر زیاد بوده که نکتهٔ مهم میان بقیه گم شده باشد. Context Engineering یعنی طراحی این‌که در هر مرحله چه چیزی به مدل برسد و چه چیزی بیرون از پنجرهٔ فعال نگه‌داری شود.

این ایده را در [نوشتهٔ اولیهٔ کانال](https://t.me/LLMEngineers/44)، و بعدتر در [یادداشت مدیریت context در taskهای طولانی](https://t.me/LLMEngineers/380) و [طراحی محیط و دسترسی Agent](https://t.me/LLMEngineers/387) باز کردم. نکتهٔ اصلی برای من این است که context فقط یک prompt ثابت نیست؛ جریان داده‌ای است که همراه task تغییر می‌کند.

## دستورالعمل مدل فقط بخشی از context است

در هر فراخوانی، مدل مجموعه‌ای از اطلاعات را می‌بیند: دستورالعمل‌ها، پیام‌های قبلی، دادهٔ task، نتیجهٔ ابزارها، سندهای بازیابی‌شده، schema ابزارها و گاهی خلاصه یا state ذخیره‌شده. prompt معمولاً شکل و اولویت بخشی از این داده‌ها را تعیین می‌کند؛ اما کیفیت سیستم به انتخاب و زمان‌بندی همهٔ این ورودی‌ها وابسته است.

پس Context Engineering جای Prompt Engineering را نمی‌گیرد. prompt می‌تواند روشن و دقیق باشد، اما اگر پاسخ API قدیمی یا سند اشتباه وارد context شده باشد، مدل همچنان تصمیم بدی می‌گیرد. برعکس، retrieval خوب هم prompt مبهم را جبران نمی‌کند.

## پنجرهٔ بزرگ به معنی context خوب نیست

پنجرهٔ context ظرفیت ورودی قابل‌مشاهده در یک فراخوانی است، نه حافظهٔ نامحدود و نه تضمین فهم همهٔ محتوا. واردکردن حجم زیاد اطلاعات هزینه را بالا می‌برد و ممکن است تمرکز مدل را از task اصلی دور کند. باید همان‌قدر context بدهیم که تصمیم بعدی را پشتیبانی کند، همراه با منبع و زمان اعتبارش.

چهار عمل ساده برای مدیریت چرخهٔ اطلاعات داریم:

**انتخاب و بازیابی.** اطلاعاتی را بیاورید که به تصمیم فعلی مربوط است. برای corpus بزرگ، جست‌وجوی ترکیبی، filter دسترسی و reranking می‌توانند کمک کنند؛ اما خود retrieval باید با queryهای واقعی ارزیابی شود.

**ثبت و نگه‌داری.** stateی که از یک فراخوانی مهم‌تر است بیرون از context ثبت کنید: شناسهٔ کار، تصمیم نهایی، نتیجهٔ ابزار یا کارهای انجام‌شده. خلاصهٔ مکالمه جای سند اصلی را نمی‌گیرد؛ اگر بعدها لازم است دلیل تصمیم بررسی شود، مدرک باید قابل‌بازیابی بماند.

**فشرده‌سازی و حذف.** وقتی history طولانی می‌شود، می‌توان پیام‌ها یا خروجی‌های حجیم را خلاصه کرد یا جزئیات را خارج از context نگه داشت. ولی همهٔ فیلدها ارزش فشرده‌سازی یکسان ندارند. شناسه، مبلغ، تاریخ، مسیر فایل و شرط پذیرش را به جمله‌ای مبهم مثل «کاربر سفارش را تأیید کرد» تبدیل نکنید.

**ایزوله‌سازی.** وظایف یا داده‌هایی را که نباید با هم مخلوط شوند از هم جدا کنید. sub-agent یا workspace جدا می‌تواند context کوچک‌تری بسازد، اما خلاصه‌ای که برمی‌گرداند ممکن است مدرکی را حذف کند. delegation باید مشخص کند چه داده‌ای را برگرداند و Agent اصلی چطور نتیجه را بررسی کند.

## مثال: Agent کدنویسی روی Repository

فرض کنید از Agent می‌خواهید یک باگ را پیدا کند. فرستادن کل repository به مدل نه عملی است و نه همیشه مفید. به‌جایش، Agent ابتدا نقشهٔ کوتاه پروژه و تست‌های مرتبط را می‌بیند، بعد فایل‌های کاندید را می‌خواند و فقط در صورت نیاز جست‌وجو را گسترش می‌دهد.

اگر خروجی shell خیلی بزرگ شد، سیستم می‌تواند آن را در فایل محلی نگه دارد و بخش مرتبط را به مدل برگرداند. اگر کار بین چند session ادامه پیدا کرد، state کوتاهی شامل هدف، فایل‌های بررسی‌شده، فرضیه‌های ردشده و تست اجراشده ذخیره می‌شود؛ اما log خام هم می‌ماند تا عامل بعدی بتواند جزئیات را دوباره بخواند.

این همان progressive disclosure است: اول نقشه و نشانی منابع، بعد فقط جزئیاتی که قدم بعدی لازم دارد. در [راهنمای Anthropic دربارهٔ context برای Agentها](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) نیز انتخاب، ساختاردهی و بازیابی context بخش محوری طراحی Agent است. راهنمای [Harness Engineering از OpenAI](https://openai.com/index/harness-engineering/) هم مثال می‌زند که یک `AGENTS.md` کوتاه و نقشه‌وار گاهی از دفترچهٔ بزرگ دستورالعمل مفیدتر است.

## چه چیزی باید وارد context شود؟

برای هر قطعه از اطلاعات این سؤال‌ها را بپرسید: آیا برای قدم بعدی لازم است؟ منبعش چیست؟ چقدر تازه است؟ آیا کاربر یا Agent حق دیدنش را دارد؟ اگر آن را حذف کنیم، امکان بازسازی وجود دارد؟ جواب این‌ها کمک می‌کند دادهٔ مهم را نگه داریم و نویز یا دادهٔ حساس غیرضروری را وارد مدل نکنیم.

پایش هم لازم است. طول prompt را ثبت کنید، ولی کیفیت را فقط با تعداد توکن نسنجید. روی taskهای نماینده بررسی کنید آیا اطلاعات درست بازیابی شد، مدل از مدرک استفاده کرد و نتیجه در صورت نیاز قابل‌ردیابی ماند. cache و خلاصه‌سازی فقط وقتی مفیدند که رفتار مطلوب حفظ شود.

## جمع‌بندی

در این نگاه، prompt می‌گوید مدل چطور با اطلاعات کار کند؛ Context Engineering مشخص می‌کند چه اطلاعاتی، در چه زمانی، با چه سطح دسترسی و در چه قالبی اصلاً به مدل برسد. برای Agentهای طولانی، از اول state پایدار، retrieval هدفمند، فشرده‌سازی قابل‌بازگشت و trace بسازید. بیشترکردن context همیشه راه‌حل نیست؛ رساندن مدرک درست به قدم درست، مسئلهٔ اصلی است.
