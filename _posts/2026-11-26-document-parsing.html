در پایان این آموزش یک Parser کوچک محلی با Python خواهید داشت، می‌دانید خروجی‌های میانی را چطور بررسی کنید و برای اسناد پیچیده‌تر یک مسیر آزمایش دارید. برای تمرین اصلی به آموزش مدل، GPU یا API پولی نیاز ندارید؛ آشنایی مقدماتی با Python کافی است.

مسیر آموزش۱. اول مشخص کنید خروجی Parser چیست ۲. یک تمرین کوچک و قابل‌تکرار بسازید ۳. از استخراج متن دیجیتال شروع کنید و مختصات را بررسی کنید ۴. صفحات اسکن‌شده و ترکیبی را با OCR پردازش کنید ۵. جدول را بازسازی کنید، نه فقط کلماتش را ۶. وقتی Baseline کافی نیست، یک Parser آگاه از Layout اضافه کنید ۷. قبل از ساخت خروجی نهایی، داده و شواهد را ساختاریافته ذخیره کنید ۸. متن چندزبانه و راست‌به‌چپ را درست مدیریت کنید ۹. مراحل را به یک Pipeline کوچک وصل کنید و خطاها را دیباگ کنید ۱۰. قبل از بهینه‌سازی، Parser را با پاسخ مرجع ارزیابی کنید ۱۱. از تمرین محلی به یک اپلیکیشن واقعی برسید برای مطالعه و تمرین بیشتر

۱. اول مشخص کنید خروجی Parser چیست

فرض کنید می‌خواهید برای دفترچه‌های راهنمای محصول، مقاله‌های پژوهشی یا اسناد یک شرکت، دستیار جست‌وجو بسازید. ورودی شما PDF، فایل Word و سند اسکن‌شده است. کاربر می‌خواهد قیمت یک کالا یا دستورالعمل مشخصی را پیدا کند. کار Parser این است که سند را به داده‌ای تبدیل کند که برنامهٔ بعدی بتواند از آن استفاده کند؛ هنوز قرار نیست به سؤال کاربر جواب بدهد.

سه مسئولیت را از هم جدا کنید: Text Extraction نویسه‌ها را می‌خواند، Layout Analysis محل پاراگراف، عنوان، جدول و تصویر را تشخیص می‌دهد و Document Parsing محتوا و روابط بین این اجزا را بازسازی می‌کند. OCR (تشخیص نوری نویسه‌ها) متن را از روی پیکسل‌های تصویر می‌خواند؛ به‌خودی‌خود ساختار جدول یا سند را بازسازی نمی‌کند.

هدفحداقل خروجی مفیدخطای احتمالی
جست‌وجو در یک دفترچهٔ راهنمامتن و شمارهٔ صفحهترتیب خواندن اشتباه
استخراج فهرست قیمتسطر، ستون، سرستون و متن خام سلولعدد درست در سطر اشتباه
ساخت RAG با استناداجزای مرتب سند و شواهد صفحه و ناحیهجواب ظاهراً درست بدون منبع قابل‌پیگیری

قرارداد ورودی و خروجی این آموزش ساده است: PDF بگیریم و JSON شامل صفحات، متن پیشنهادی، کلمات همراه مختصات، سلول‌های جدول ساده و هشدارها بسازیم. بعد برای ساختارهای پیچیده از ابزار آگاه از Layout استفاده می‌کنیم و Markdown و HTML را برای مطالعهٔ انسان تولید می‌کنیم. این نقطهٔ شروع است، نه یک Parser همه‌کاره.

چرا از همان اول PDF را به یک LLM ندهیم؟ این روش گاهی Baseline مناسبی است، ولی اگر مدل عددی را اشتباه خواند، همچنان باید بتوانید منبع آن را پیدا کنید، خروجی‌ها را مقایسه کنید و کیفیت را بسنجید. اول مسیر شواهد را بسازید.

۲. یک تمرین کوچک و قابل‌تکرار بسازید

به Python نسخهٔ ۳٫۱۰ یا جدیدتر و یک ترمینال نیاز دارید. این سه فایل را در یک پوشهٔ خالی ذخیره کنید: requirements.txt، make_demo.py و parse_pdf.py. برای قابل‌تکرار بودن تمرین، نسخهٔ PyMuPDF را ثابت کرده‌ایم؛ برای استفاده در سرویس واقعی، نسخه‌های جدیدتر و اصلاحات امنیتی را بررسی کنید. PyMuPDF با مجوز AGPL یا مجوز تجاری عرضه می‌شود؛ قبل از استقرار، شرایط مجوز را بخوانید.

python -m venv .venv
# Linux / macOS:
source .venv/bin/activate
# Windows PowerShell (instead of the line above):
# .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python make_demo.py demo.pdf

فایل make_demo.py یک PDF کاملاً مصنوعی به نام demo.pdf با سه صفحه می‌سازد:

  1. یک صفحهٔ متنی دیجیتال با عنوان Project guide.
  2. یک جدول دیجیتال با سرستون‌های Item و Price و دو ردیف Notebook (12.50) و Pen (2.00).
  3. یک صفحهٔ صرفاً تصویری با عبارت Scan example و کد مرجع AB123.

PDF را در یک برنامهٔ نمایش سند باز کنید و سعی کنید متن هر صفحه را انتخاب کنید. در دو صفحهٔ اول می‌توانید متن را انتخاب کنید؛ صفحهٔ سوم فقط تصویر است. از قبل می‌دانیم محتوای صحیح هر صفحه چیست، پس یک Ground Truth (پاسخ مرجع) کوچک برای دیباگ داریم. بهتر است تمرین را با اسناد محرمانهٔ مشتری شروع نکنید.

۳. از استخراج متن دیجیتال شروع کنید و مختصات را بررسی کنید

کد زیر را در فایل inspect_pdf.py قرار دهید و با Python اجرا کنید. این کد لایهٔ متن داخل PDF را می‌خواند، نه پیکسل‌های صفحه را.

import pymupdf

with pymupdf.open("demo.pdf") as doc:
    for page in doc:
        print(f"Page {page.number + 1}")
        print(page.get_text("text", sort=True))

انتظار داریم در صفحات ۱ و ۲ متن بگیریم، اما صفحهٔ ۳ متن قابل‌استفاده نداشته باشد. PDF ممکن است دستورهای رسم متن را با ترتیبی ذخیره کرده باشد که با ترتیب مطالعهٔ انسان فرق دارد. بعضی اسکن‌ها هم یک لایهٔ نامرئی متن OCR دارند که خودش ممکن است اشتباه باشد. پس غیرخالی بودن متن، اثبات صحت استخراج نیست. توضیحات pypdf دربارهٔ استخراج متن PDF و راهنمای استخراج متن PyMuPDF را ببینید.

برای دیباگ ترتیب خواندن از مختصات استفاده کنید. Bounding Box یا BBox چهار مختصات است که جای یک کلمه یا ناحیه را روی صفحه مشخص می‌کند. در این مثال مختصات PyMuPDF مربوط به صفحهٔ بدون چرخش و برحسب Point هستند، نه پیکسل.

with pymupdf.open("demo.pdf") as doc:
    page = doc[0]
    for x0, y0, x1, y1, text, block, line, word in page.get_text("words"):
        print(text, (x0, y0, x1, y1))
    page.get_pixmap(dpi=150).save("page-1.png")

خروجی را با page-1.png مقایسه کنید. اگر سند دو ستون دارد، بلوک‌ها را با page.get_text("blocks") بگیرید، کادرشان را روی کپی یا تصویر صفحه رسم کنید و ببینید ترتیب خواندن بین ستون‌ها جابه‌جا شده یا نه. گزینهٔ sort=True یک روش هندسی کمکی است، نه راه‌حل قطعی همهٔ Layoutها یا اسناد راست‌به‌چپ. برای Layout ساده می‌توانید ابتدا بلوک‌ها را بر اساس ستون گروه‌بندی کنید و داخل هر ستون مرتبشان کنید؛ برای موارد پیچیده سراغ مرحلهٔ ۶ بروید.

اگر PDF از ابتدا دیجیتال بوده و متن درست کدگذاری شده، استخراج Native نقطهٔ شروع خوبی است. صرفاً چون OCR داریم، لازم نیست آن را برای همهٔ صفحات اجرا کنیم.

۴. صفحات اسکن‌شده و ترکیبی را با OCR پردازش کنید

موتور Tesseract و فایل‌های زبان موردنیاز را نصب کنید. برای سیستم‌عامل‌های دیگر از راهنمای نصب استفاده کنید. فهرست زبان‌ها باید برای تمرین مصنوعی ما شامل eng باشد؛ کد فارسی fas و کد عربی ara است (فهرست کد زبان‌ها).

# Ubuntu / Debian (install language data as needed):
sudo apt install tesseract-ocr tesseract-ocr-eng tesseract-ocr-fas
tesseract --list-langs
with pymupdf.open("demo.pdf") as doc:
    page = doc[2]  # 0-based index: page 3
    tp = page.get_textpage_ocr(language="eng", dpi=300, full=True)
    print(page.get_text("text", textpage=tp, sort=True))

انتظار داریم متن پیشنهادی شامل AB123 باشد. اگر Tesseract فایل زبانش را پیدا نکرد، مسیر پوشه‌ای که فایل‌های .traineddata در آن هستند را با پارامتر tessdata یا گزینهٔ --tessdata اسکریپت مشخص کنید. حتماً TextPage حاصل از OCR را به تابع استخراج بعدی بدهید؛ وگرنه دوباره همان لایهٔ Native را می‌خوانید.

برای سند ترکیبی فارسی و انگلیسی، language="fas+eng" را امتحان کنید. از حدود ۳۰۰ DPI شروع کنید و روی نمونه‌های خودتان مقایسه بگیرید. رزولوشن بالاتر حافظه و زمان بیشتری مصرف می‌کند و جزئیاتی را که از ابتدا در اسکن وجود نداشته‌اند برنمی‌گرداند. با کمک راهنمای کیفیت Tesseract اصلاح کجی، چرخش، کنتراست، حذف نویز یا تنظیم روش قطعه‌بندی صفحه را یکی‌یکی امتحان کنید. همیشه نتیجه را با تصویر اصلی مقایسه کنید؛ به‌خصوص نقطهٔ اعشار و نویسه‌های ریز را.

اگر هدفتان ساخت PDF قابل‌جست‌وجو است، OCRmyPDF پس از نصب خود ابزار و وابستگی‌هایش یک مسیر جداگانه و کاربردی دارد:

ocrmypdf -l fas+eng --rotate-pages --deskew --skip-text input.pdf searchable.pdf

فایل اصلی input.pdf را دست‌نخورده نگه دارید. گزینهٔ --skip-text صفحات دارای متن را رد می‌کند؛ بنابراین ممکن است تصویرِ حاوی متن را در صفحه‌ای که یک عنوان دیجیتال دارد نخواند. قابل‌جست‌وجو شدن PDF هم به‌معنی بازسازی جدول نیست. حالت‌های مختلف OCR روی اسناد ترکیبی را در راهنمای OCRmyPDF ببینید.

قاعدهٔ مسیریابی: متن Native خالی، نویسهٔ جایگزین، ناحیهٔ جاافتاده و ترتیب خواندن خراب، نشانه‌هایی برای بازبینی هستند؛ نه یک تشخیص‌دهندهٔ بی‌نقص اسکن. صفحهٔ سفید می‌تواند معتبر باشد؛ اما صفحه‌ای که یک عنوان دیجیتال و یک جدول اسکن‌شده دارد هنوز کامل Parse نشده است. در صفحات ترکیبی ناحیه‌های تصویری را بررسی کنید و در صورت نیاز فقط ناحیهٔ خوانده‌نشده را OCR کنید. اسکریپت آموزشی امکان OCR کامل صفحات انتخابی را دارد؛ بازیابی در سطح ناحیه قدم بعدی است و در Baseline پیاده نشده است.

۵. جدول را بازسازی کنید، نه فقط کلماتش را

صفحهٔ دوم تمرین ما چنین جدولی دارد:

کالا (Item)قیمت (Price)
Notebook12.50
Pen2.00

گرفتن یک لیست از کلمات کافی نیست. باید بدانیم عدد 12.50 مربوط به Notebook است، نه Pen. روی جدول سادهٔ تمرین، تشخیص جدول PyMuPDF را امتحان کنید:

with pymupdf.open("demo.pdf") as doc:
    for table in doc[1].find_tables().tables:
        for row in table.extract():
            print(row)

خروجی مورد انتظار سه سطر ['Item', 'Price']، ['Notebook', '12.50'] و ['Pen', '2.00'] است. مستندات Page.find_tables استراتژی‌های مبتنی بر خطوط و متن را توضیح می‌دهند. برای جدول بدون خطوط مرزی، روی چند صفحه strategy="text" را هم امتحان و مقایسه کنید. پیدا نشدن جدول، دلیل بر نبود جدول نیست.

اسکن، سلول ادغام‌شده، سرستون چندسطحی و جدولی که بین صفحات شکسته شده، بیشتر از تشخیص خطوط نیاز دارند. شناسهٔ سطر و ستون، تعداد سطر و ستون پوشش‌داده‌شده توسط سلول ادغام‌شده (Span) در صورت معلوم بودن، ارتباط با سرستون و مختصات را ذخیره کنید. تفاوت سلول خالی، سلول ادغام‌شده و سلول ناخوانا را حفظ کنید. برای وصل کردن جدول بین دو صفحه، سرستون‌های تکراری، هم‌ترازی ستون‌ها، بخش سند و مرز صفحه را مقایسه کنید؛ صرف برابر بودن تعداد ستون‌ها دلیل ادغام دو جدول نیست.

وقتی جدول عدد، واحد یا شناسه دارد، علاوه بر درستی متن، ارتباط آن با سطر و ستون درست را هم بررسی کنید. ممکن است موتور OCR همهٔ نویسه‌ها را درست خوانده باشد ولی بازسازی ساختار، مقدار را به سلول اشتباه نسبت دهد. برای Layout پیچیده، در مرحلهٔ بعد ابزار آگاه از ساختار را امتحان می‌کنیم.

۶. وقتی Baseline کافی نیست، یک Parser آگاه از Layout اضافه کنید

حالا یک سند واقعی و مجاز را امتحان کنید؛ مثلاً یک گزارش عمومی که عنوان، جدول و متن دوستونه دارد. Docling به‌جای رشتهٔ متن ساده، نمایش ساختاریافته‌ای از سند ارائه می‌دهد. اگر به این مرحله نیاز دارید، آن را جداگانه نصب کنید؛ اولین تبدیل PDF ممکن است فایل‌های مدل را دانلود کند و بیشتر طول بکشد. مثال زیر بر اساس Quickstart پایتون و API خروجی Docling است:

python -m pip install docling
from pathlib import Path
from docling.document_converter import DocumentConverter

result = DocumentConverter().convert("input.pdf")
doc = result.document
doc.save_as_json(Path("document.json"))
Path("document.md").write_text(
    doc.export_to_markdown(), encoding="utf-8"
)

JSON را برای بررسی اجزای ساختاریافته و Markdown را برای پیش‌نمایش خوانا استفاده کنید. مدل سند Docling آیتم‌های متنی، جدول، تصویر، روابط درختی و اطلاعات منبع را توضیح می‌دهد. قبل از فعال کردن OCR، تشخیص ساختار جدول یا مدل خاص، تنظیمات Pipeline را بخوانید؛ پشتیبانی و تنظیمات بین نسخه‌ها فرق می‌کنند. فرض نکنید OCR پیش‌فرض حتماً روی زبان موردنیاز شما کیفیت خوبی دارد. این مثال اختیاری بر اساس مستندات نوشته شده و جزو تست تمرین کوچک PyMuPDF نیست.

گزینه‌های دیگر هم داریم؛ مثلاً Unstructured که روش‌های مختلفی برای تقسیم PDF به اجزا دارد، یا خواننده‌های Native. ساده‌ترین ابزاری را انتخاب کنید که نیاز اندازه‌گیری‌شدهٔ شما را برآورده می‌کند. این جدول رتبه‌بندی قطعی نیست:

ابزارچه زمانی سراغش برویم؟چه چیزی را بررسی کنیم؟
PyMuPDF / pypdfمتن دیجیتال PDF و شواهد پایه کافی استترتیب خواندن، Encoding، مجوز
Tesseract / OCRmyPDFتبدیل تصویر به متن یا PDF قابل‌جست‌وجو می‌خواهیمفایل زبان، کیفیت اسکن، ناحیه‌های جاافتاده
Doclingعنوان‌ها، ترتیب خواندن، جدول و فرمت‌های ساختاریافته مهم‌اندپشتیبانی زبان OCR، دقت جدول، زمان اجرا
Unstructuredاجزای دسته‌بندی‌شدهٔ سند و روش‌های جایگزین Partition لازم استوابستگی‌ها، انتخاب استراتژی، ترتیب ستون‌ها
مدل بینایی‌ـ‌زبانی (VLM)برای یک ناحیهٔ دشوار به یک خوانش بصری دیگر نیاز داریمHallucination، سیاست دادهٔ حساس، هزینه، قابلیت بررسی

برای فهم Trade-off روش‌ها، راهنمای Partitioning در Unstructured را بخوانید. برای DOCX، XLSX، HTML و ورودی‌هایی که ذاتاً ساختار دارند، از خوانندهٔ مخصوص همان فرمت یا مبدلی مثل Docling با فهرست فرمت‌های پشتیبانی‌شده استفاده کنید. لازم نیست همه‌چیز را PDF کنید تا به OCR بدهید؛ عنوان‌های Word و سلول‌های اکسل از ابتدا ساختار مفیدی دارند.

VLM ممکن است برای اسکن غیرمعمول یا نمودار مفید باشد. فقط ناحیهٔ لازم را ارسال کنید، خوانش تحت‌اللفظی با Schema مشخص بخواهید، برای موارد نامعلوم مقدار null بگذارید، تصویر ناحیه را نگه دارید و خروجی را بررسی کنید. جواب مدل یک گزینهٔ پیشنهادی دیگر است؛ توافق دو مدل به‌تنهایی اثبات درستی نیست.

۷. قبل از ساخت خروجی نهایی، داده و شواهد را ساختاریافته ذخیره کنید

حالا یک نمایش اصلی برای داده انتخاب کنید؛ همان نسخه‌ای که خروجی‌های دیگر از روی آن ساخته می‌شوند. می‌توانید Schema یک ابزار موجود را به کار بگیرید یا ساختار کوچکی برای خودتان تعریف کنید. DocumentIR (Intermediate Representation) صرفاً نمایش میانی ساختاریافتهٔ سند بین استخراج و خروجی است؛ فرمت اجباری یا استاندارد واحد صنعت نیست.

{
  "page": 2,
  "kind": "table_cell",
  "table_id": "p2-t0",
  "row": 1,
  "col": 1,
  "header": "Price",
  "text_raw": "12.50",
  "value": "12.50",
  "bbox": [200, 85, 360, 120],
  "method": "native",
  "status": "unverified"
}

این یک Schema آموزشی برای سلول معلوم در تمرین است، نه رکورد عیناً تولیدشده توسط اسکریپت. اندیس‌ها از صفر و شمارهٔ صفحه از یک شروع می‌شوند؛ BBox مرز موردانتظار سلول در مختصات Point صفحهٔ بدون چرخش را نشان می‌دهد. در عمل هش سند، شناسهٔ صفحه و ناحیه، موتور و نسخه، تنظیمات و در صورت تغییر اندازه یا چرخش تصویر، تبدیل مختصات را هم ثبت کنید. اگر مقداری را نرمال کردید، متن خام را نگه دارید. برای مبلغی که به محاسبات اعشاری دقیق نیاز دارد از Decimal به‌جای Float دودویی استفاده کنید.

خروجی Parser باید مشخص کند چه چیزی معلوم است، چه چیزی جا افتاده و کدام ناحیه هنوز حل نشده است. JSON برای اعتبارسنجی و نرم‌افزار بعدی مفید است؛ HTML از جدول‌های پیچیده‌تری پشتیبانی می‌کند؛ Markdown برای مطالعه یا پرامپت مدل راحت است، ولی ممکن است اطلاعات سلول ادغام‌شده یا منبع را از دست بدهد. Markdown را خروجی مشتق‌شده بدانید، نه تنها نسخهٔ شواهد. برای نمایش متن یا HTML استخراج‌شده در مرورگر هم Escaping یا Sanitization انجام دهید.

۸. متن چندزبانه و راست‌به‌چپ را درست مدیریت کنید

فارسی، عربی و عبری یک چالش دیگر دارند: ترتیب منطقی نویسه‌های Unicode با ترتیب نمایش آن‌ها روی صفحه یکی نیست. عبارت مبلغ ۱۲٫۵۰ USD را ببینید؛ کلمهٔ راست‌به‌چپ، عدد اعشاری و کد ارز چپ‌به‌راست کنار هم‌اند. معکوس کردن کل رشته با text[::-1] می‌تواند عدد و عبارت انگلیسی را خراب کند. الگوریتم دوجهتهٔ Unicode ترتیب نمایش را توضیح می‌دهد؛ متن خراب استخراج‌شده را تعمیر نمی‌کند.

رشتهٔ اصلی Unicode را نگه دارید. برای جست‌وجو یک نسخهٔ نرمال‌شدهٔ جدا با NFC و تبدیل‌های زبانی حساب‌شده بسازید. برای فارسی، اگر نیاز کاربرد جست‌وجو چنین است، می‌توان ی و ک عربی را به معادل فارسی تبدیل کرد:

import unicodedata

def normalize_for_search(text):
    text = unicodedata.normalize("NFC", text)
    return text.translate(str.maketrans({
        "ي": "ی", "ك": "ک"
    }))

raw = "مبلغ ۱۲٫۵۰ USD"
search_text = normalize_for_search(raw)
# Keep raw as well; do not reverse or strip every symbol.

از API نرمال‌سازی Unicode در Python استفاده کنید. نیم‌فاصله، نشانه‌گذاری، منفی، درصد و جداکنندهٔ اعشار را کورکورانه حذف نکنید؛ ممکن است معنای متن به آن‌ها وابسته باشد. تبدیل ارقام را فقط در لایهٔ مشخص جست‌وجو یا پردازش عدد انجام دهید و صفرهای ابتدایی شناسه‌ها و رشتهٔ اصلی را حفظ کنید. روی ترکیب واژه‌های فارسی، عربی و انگلیسی، تاریخ، واحد پول، شناسه، پرانتز و سلول‌های چندجهتهٔ جدول تست بگیرید. در رابط نمایش از RTL و جداسازی جهت متن ترکیبی استفاده کنید. اگر استخراج خراب است، قبل از هر اصلاحی ترتیب خام نویسه‌ها، مختصات کلمات و تصویر صفحه را بررسی کنید.

۹. مراحل را به یک Pipeline کوچک وصل کنید و خطاها را دیباگ کنید

اسکریپت کامل تمرین، استخراج Native، مسیریابی در سطح صفحه، OCR اختیاری، مختصات کلمات، جدول دیجیتال ساده و هشدارها را کنار هم قرار می‌دهد. روی همان PDF تمرین دو بار با نام خروجی متفاوت اجرا کنید:

python parse_pdf.py demo.pdf native.json
python parse_pdf.py demo.pdf with-ocr.json --ocr --lang eng
# Optional: inspect and explicitly OCR a mixed/corrupted page:
python parse_pdf.py input.pdf review.json --ocr --lang fas+eng --ocr-page 2

دو JSON را باز کنید. در native.json، صفحهٔ ۳ روش استخراج ندارد و نیازمند بازبینی است. در with-ocr.json برای همان اسکن یک متن پیشنهادی از OCR داریم، ولی لیست جدول‌ها خالی مانده چون OCR سلول‌های جدول را بازسازی نکرده است. صفحهٔ ۲ جدول دیجیتال تشخیص‌داده‌شده را دارد. کل سند همچنان unverified است؛ حتی صفحه‌ای با وضعیت candidate هنوز پذیرفته نشده است. گزینهٔ --ocr-page صریحاً درخواست OCR کامل صفحه را می‌دهد و متن Native اصلی را برای مقایسه نگه می‌دارد، اما استخراج جدول Native در آن صفحه انجام نمی‌شود.

Input file
  -> Detect format / inspect pages
  -> Native extraction OR OCR
  -> Layout + reading order + tables (when needed)
  -> Structured document + source coordinates
  -> Validate / review unresolved regions
  -> Export JSON / Markdown / HTML
  -> Chunk + index accepted content only

همهٔ مدل‌ها و تکنیک‌های پیشرفته را یک‌جا اضافه نکنید. وقتی نتیجه خراب است، خروجی میانی را با تصویر صفحه مقایسه کنید، مرحلهٔ خطادار را پیدا کنید و فقط همان مرحله را تغییر دهید. این جدول نقطهٔ شروع خوبی برای دیباگ است:

Retry باید محدود باشد. خروجی خام را جدا از اصلاحات نگه دارید و برای ناحیهٔ حل‌نشده صف بازبینی داشته باشید. شکست یک مرحله نباید بی‌صدا به خروجی خالی اما موفق تبدیل شود. در سرویس خودکار فقط عناصر تأییدشده را به بخش بعدی بدهید؛ اگر ناحیهٔ نامعلوم می‌تواند معنی سند را عوض کند، انتشار کل سند را متوقف کنید. این مثال عمداً پذیرش خودکار، مسیریابی کالیبره‌شده، بازسازی جدول ادغام‌شده و ایزوله‌سازی سطح سرویس ندارد.

۱۰. قبل از بهینه‌سازی، Parser را با پاسخ مرجع ارزیابی کنید

از یک تست کوچک روی تمرین مصنوعی شروع کنید. کد زیر را با نام check_demo.py ذخیره کنید و بعد از اجرای مثال OCR آن را اجرا کنید.

import json

with open("with-ocr.json", encoding="utf-8") as f:
    parsed = json.load(f)
assert parsed["page_count"] == 3
assert len(parsed["pages"]) == 3

cells = {
    (cell["row"], cell["col"]): cell["text"]
    for cell in parsed["pages"][1]["tables"][0]["cells"]
}
assert cells[(1, 0)] == "Notebook"
assert cells[(1, 1)] == "12.50"
assert cells[(2, 1)] == "2.00"
assert "AB123" in parsed["pages"][2]["text"]
# This checks a synthetic fixture, not production quality.

بعد یک Gold Dataset بسازید؛ صفحاتی واقعی و مجاز با متن مرجع، ترتیب خواندن، ساختار جدول و فیلدهای کلیدی که دستی بررسی شده‌اند. خانواده‌های متفاوت سند را پوشش دهید: دیجیتال، اسکن، ترکیبی، دوستونه، چرخیده، کم‌کیفیت و چندزبانه؛ نه فقط صفحاتی که ابزار همین حالا خوب می‌خواند. مجموعهٔ ارزیابی را ثابت نگه دارید و تنظیمات را روی اسناد دیگری انتخاب کنید. تعداد صفحات به تنوع و ریسک بستگی دارد؛ چند صفحهٔ مصنوعی نمی‌تواند کیفیت کل اسناد شما را اثبات کند.

مثلاً در یک متن فرضی هزارنویسه‌ای، اگر فقط ده نویسه جایگزین شده باشند، CER برابر یک درصد است. اما اگر یکی از آن‌ها قیمت 12.50 را به 12.90 تبدیل کرده باشد، همان فیلد از نظر Exact Match شکست خورده است. میانگین به‌تنهایی کافی نیست.

OmniDocBench مرجع خوبی برای تفکیک ارزیابی متن، جدول، فرمول و ترتیب خواندن است؛ OHR-Bench هم نشان می‌دهد چرا نویز OCR در مراحل بعدی RAG اهمیت دارد. هیچ‌کدام اثبات کیفیت روی اسناد و زبان‌های شما نیستند. تست مخصوص کاربرد بسازید و آستانه را با توجه به هزینهٔ خطا تعیین کنید. تنظیمات، نسخهٔ دیتاست و موارد شکست را ثبت کنید. فقط وقتی مقایسهٔ کنترل‌شده بهبود ارزشمندی نشان می‌دهد، پیچیدگی بیشتری اضافه کنید.

۱۱. از تمرین محلی به یک اپلیکیشن واقعی برسید

وقتی نمایش ساختاریافته برای کاربرد شما به کیفیت مناسب رسید، از روی آن Chunkهای بازیابی را بسازید. عنوان را همراه پاراگراف، سرستون را همراه ردیف مرتبط و Caption را همراه تصویر نگه دارید. شمارهٔ صفحه و شناسهٔ عنصر را در متادیتای Chunk ذخیره کنید تا جواب RAG به شواهد لینک شود. محدودیت اندازهٔ Chunk را با Tokenizer مدل Embedding واقعی انتخاب و کیفیت بازیابی را اندازه‌گیری کنید. Docling برای شروع آماده، Chunking آگاه از ساختار را مستند کرده است. کیفیت Parsing، Retrieval و جواب نهایی باید جداگانه ارزیابی شوند.

برای سرویس، تبدیل سند را پشت Worker یا صف با منابع محدود بگذارید. دریافت فایل، Parse، بازبینی و انتشار را جدا کنید. فایل اصلی، هش محتوا، Artifact خام، تنظیمات و خروجی نسخه‌دار را نگه دارید. نوع و اندازهٔ فایل، تعداد صفحه و پیکسل، Timeout، حافظه و تعداد اجرای هم‌زمان را محدود کنید؛ از Worker ایزوله و بدون دسترسی اضافه یا شبکهٔ غیرضروری استفاده کنید. فایل‌های Office ممکن است هنگام بازشدن فشرده‌سازی حجم بسیار بیشتری پیدا کنند. اسکریپت آموزشی را مستقیم به Endpoint آپلود عمومی تبدیل نکنید. راهنمای امنیت OCRmyPDF توضیح می‌دهد چرا نباید PDF را ذاتاً امن فرض کنیم.

قبل از فرستادن سند به سرویس OCR یا VLM خارجی، محرمانگی و سیاست نگهداری داده را بررسی کنید. دستورهای داخل سند را دادهٔ غیرقابل‌اعتماد بدانید، نه دستور ایجنت؛ خروجی قابل‌نمایش را Sanitization کنید و دسترسی به سند و Artifact را محدود کنید. برای عملکرد، خروجی خام موفق را با کلید شامل محتوا و تنظیمات Cache کنید، اجرای Cache-hit را از ارزیابی تازه جدا کنید و قبل از Batching یا مدل تخصصی، روی بار کاری واقعی Benchmark بگیرید.

چک‌لیست انتشار: تست رگرسیون Gold Dataset را اجرا کنید؛ مطمئن شوید همهٔ صفحات وضعیت مشخص دارند؛ ناحیهٔ جاافتاده یا مشکوک را بازبینی کنید؛ جدول و فیلد حساس را بررسی کنید؛ پیوندهای منبع را تأیید کنید؛ هزینه و تأخیر را بسنجید؛ ورودی‌های پشتیبانی‌نشده و Rollback را مستند کنید. بعد دادهٔ پذیرفته‌شده را ایندکس یا منتشر کنید. این‌ها پیشنهاد مهندسی‌اند، نه ادعای اینکه اسکریپت آموزشی همه‌شان را انجام می‌دهد.

با سه سند و یک تست کوچک شروع کنید. اول راهش بیندازید، گلوگاه واقعی را پیدا کنید، همان را اصلاح کنید و دوباره اندازه بگیرید. مسیر تبدیل یک اسکریپت استخراج به Pipeline قابل‌اتکا همین است.

برای مطالعه و تمرین بیشتر

یک مقالهٔ عمومی دوستونه، یک اسکن فارسی و یک جدول بدون خط مرزی را امتحان کنید. برای هرکدام فایل اصلی را نگه دارید، چند ناحیهٔ مرجع را دستی مشخص کنید، دو مسیر منطقی را اجرا کنید و متن، ساختار، صحت فیلد و زمان اجرا را مقایسه کنید. برای نمودار یا فرم، Schema روشن تعریف کنید و به‌جای اعتماد به توضیح تولیدشدهٔ مدل، مقدار را با منبع تطبیق دهید.

  • راهنمای استخراج متن PyMuPDF و مشکلات رایج استخراج
  • راهنمای بهبود کیفیت OCR در Tesseract و راهنمای OCRmyPDF
  • Quickstart Docling، ساختار سند و تنظیمات Pipeline
  • روش‌های Partitioning در Unstructured
  • Unicode UAX #9: الگوریتم دوجهته
  • OmniDocBench و OHR-Bench

مثال‌ها و معماری پیشنهادی آموزشی و مستقل از پروژهٔ خاصی هستند. تمرین سه‌صفحه‌ای مصنوعی است، نه Benchmark یک Parser تجاری یا متن‌باز. لینک مستندات برای APIها و مفاهیم است؛ انتخاب ابزار و معماری Production به کاربرد شما بستگی دارد.
