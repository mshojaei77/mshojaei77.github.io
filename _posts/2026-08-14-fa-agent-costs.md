# هزینهٔ واقعی Agent چطور محاسبه می‌شود؟

وقتی یک Agent چند بار مدل را صدا می‌زند، هزینهٔ یک کار برابر با هزینهٔ اولین prompt نیست. context قبلی، خروجی ابزارها، درخواست‌های تکراری و طول پاسخ‌ها در هر گام جمع می‌شوند. کم‌شدن متن خروجی ابزار هم لزوماً صورتحساب یا هزینهٔ هر کار موفق را کم نمی‌کند؛ باید کل مسیر اجرا را اندازه گرفت.

## صورت‌حساب یک Agent از چه چیزهایی ساخته می‌شود؟

برای یک کار واحد، این اجزا را جدا ثبت کنید:

- **درخواست‌های مدل:** ورودی تازه، ورودی cacheشده، خروجی، reasoning یا tokenهای داخلیِ قابل‌صورتحساب در API.
- **تکرارها:** اصلاح prompt، retry پس از خطا، فراخوانی دوبارهٔ ابزار و اجرای مجدد کار.
- **ابزارها:** جست‌وجو، مرورگر، اجرای کد، پایگاه داده، sandbox یا APIهای بیرونی.
- **زیرساخت:** زمان GPU/CPU، ذخیره‌سازی، شبکه، صف و observability.
- **بازبینی انسانی:** زمان اصلاح، review و رسیدگی به خروجی ناموفق.

برای API پرداختی می‌توان هزینهٔ متغیر را به شکل ساده نوشت:

```text
هزینهٔ مدل = Σ هر درخواست:
  (ورودی تازه × نرخ ورودی)
  + (ورودی cacheشده × نرخ cache)
  + (خروجی × نرخ خروجی)
```

قیمت و طبقه‌بندی tokenها بین ارائه‌دهنده‌ها و نسخه‌ها عوض می‌شود؛ از نرخ زندهٔ endpoint خودتان استفاده کنید و در مقاله یا داشبورد بدون تاریخ عدد ثابت ننویسید. در مدل self-hosted، صورت‌حساب API ممکن است صفر باشد ولی هزینهٔ compute، برق، استهلاک، عملیات و فرصت همچنان وجود دارد.

## چرا context compaction می‌تواند صرفه‌جویی را برعکس کند؟

اگر ابزار خروجی ۱۰ هزار token بدهد و فشرده‌ساز آن را به ۲ هزار برساند، این عدد به‌تنهایی هزینهٔ کل را معلوم نمی‌کند. باید ببینیم مدل پس از دیدن خلاصه کار را تمام می‌کند یا دوباره همان فایل را می‌خواند، جست‌وجوی تازه می‌زند و patch را تکرار می‌کند. حذف یک شمارهٔ خط، error code یا بخش لازم برای تغییر کد ممکن است تعداد رفت‌وبرگشت را بالا ببرد.

یک مطالعهٔ [Token Reduction Is Not Cost Reduction](https://arxiv.org/abs/2607.12161) حدود ۲٬۹۰۸ اجرای billed از Claude Code را بررسی کرد که ۲٬۸۴۸ مورد وارد تحلیل شدند. در setup گزارش‌شده، یک بازوی کاهش خروجی خام ابزار را حدود ۳۸٪ کم کرد اما هزینهٔ واقعی جفت‌شده ۶٫۸٪ بیشتر شد. در آزمون patch کوچک مبتنی بر SWE-bench-derived Go هم تعداد patchهای اعمال‌شده از ۲۷/۴۰ به ۱۵/۴۰ رسید، چون compression، anchorهای دقیق و verbatim را خراب کرده بود.

این اعداد نتیجهٔ یک سیستم، مدل، مجموعه task و طراحی آزمایش مشخص‌اند؛ نمی‌گویند هر compression هزینه را افزایش می‌دهد. همان مقاله استدلال می‌کند که رابطهٔ کاهش token ابزار و هزینهٔ صورتحساب‌شده در داده‌هایش ضعیف بوده است. برای محصول خودتان، باید هزینه و موفقیت را باهم اندازه بگیرید.

## معیار درست: هزینهٔ هر کار موفق

به‌جای نمودار «token ذخیره‌شده»، برای هر task این مقدار را نگه دارید:

```text
هزینهٔ هر کار موفق = کل هزینهٔ اجراها ÷ تعداد کارهای موفق
```

در این محاسبه، موفقیت را با معیار مستقل تعریف کنید: تست‌ها pass شوند، پاسخ از نظر factuality بررسی شود یا کاربر نتیجه را تأیید کند. اگر task فقط در ۷۰٪ موارد موفق است، ارزان‌بودن اجرای اول ممکن است با retry و review جبران شود.

برای یک Agent کدنویسی، ثبت این metricها مفید است: billed cost، تعداد model call، input/output/cache token، tool call، retry، wall-clock، pass rate، patch acceptance و زمان review. اگر فشرده‌ساز دارید، زمان و resource خود فشرده‌ساز را هم حساب کنید. بدون این داده‌ها نمی‌دانید کاهش output از کدام بخش هزینه آمده است.

## از کجا بهینه‌سازی را شروع کنیم؟

۱. **یک workload واقعی انتخاب کنید.** taskها را بر اساس نوع و سختی تفکیک کنید؛ یک نمونهٔ آسان نمایندهٔ Agent نیست.
۲. **خط پایه را اندازه بگیرید.** نسخهٔ مدل، prompt، ابزار، محدودیت retry و شرایط cache را ثابت کنید.
۳. **یک تغییر اعمال کنید.** مثلاً خروجی ابزار را محدود کنید یا یک retrieval بهتری بسازید.
۴. **با موفقیت برابر مقایسه کنید.** اگر کیفیت افت کرد، «صرفه‌جویی» ممکن است هزینه را به کاربر یا تیم منتقل کرده باشد.
۵. **نتیجه را در چند run بسنجید.** اختلاف prompt cache، variance مدل و taskها می‌توانند روی چند نمونه نتیجه را منحرف کنند.

هدف من از محدودکردن خروجی ابزارها این نیست که هر چیزی را کوتاه کنیم؛ مدل باید برای تصمیم بعدی context کافی داشته باشد، و جزئیات قابل‌بازیابی باید در archive بمانند. گاهی یک فایل log مرتب و یک ابزار `recall` از خلاصهٔ خیلی کوتاه، هم ارزان‌تر است هم قابل‌اعتمادتر.

## جمع‌بندی

یک Agent یک حلقه است و هزینه‌اش را باید در سطح کل حلقه سنجید. تعداد tokenهای خروجی ابزار فقط یکی از ورودی‌های آن است؛ prompt cache، retry، ابزار و موفقیت نهایی هم اهمیت دارند. فشرده‌سازی را وقتی حفظ کنید که روی workload شما هزینهٔ هر کار موفق را پایین بیاورد و شواهد لازم برای اجرای درست را نگه دارد.
