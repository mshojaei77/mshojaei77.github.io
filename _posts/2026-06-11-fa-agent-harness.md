# هارنس Agent چیست؟ چرا انتخاب مدل کافی نیست؟

اگر یک Agent در دمو خوب جواب می‌دهد ولی وسط کار فایل اشتباه را تغییر می‌دهد، ابزار را دوباره صدا می‌زند یا بدون بررسی می‌گوید «تمام شد»، عوض‌کردن مدل احتمالاً اولین کاری نیست که باید بکنی. معمولاً مشکل در لایه‌ای است که مدل را به ابزارها و محیط واقعی وصل می‌کند؛ همان چیزی که به آن Agent Harness می‌گوییم.

برای اینکه Agent در عمل قابل‌کنترل باشد، باید مدل، ابزارها، state، مجوزها، کنترل خطا و معیارهای توقف را در یک محیط اجرایی مشخص کنار هم طراحی کرد. این اجزا را می‌توان به‌صورت یک harness مهندسی منسجم دید.

## هارنس دقیقاً چیست؟

به‌عنوان یک مدل ذهنی می‌شود گفت: **Agent = Model + Harness**. این معادله تعریف رسمی و کاملی نیست؛ کمک می‌کند دو مسئولیت را از هم جدا کنیم. مدل متن را می‌فهمد و پیشنهاد می‌دهد قدم بعدی چه باشد. Harness تصمیم می‌گیرد آن پیشنهاد چطور اجرا شود، چه اطلاعاتی در اختیار مدل باشد، چه نتیجه‌ای برگردد و کدام کارها اجازهٔ اجرا دارند.

برای مثال، مدل می‌تواند پیشنهاد کند `pytest` اجرا شود یا یک فایل ویرایش شود. خودش به‌تنهایی به ترمینال دسترسی ندارد. Harness فراخوانی ابزار را می‌گیرد، آن را در محیط تعریف‌شده اجرا می‌کند، خروجی را جمع می‌کند و نتیجه را به مرحلهٔ بعد می‌فرستد. همین لایه می‌تواند اجرای یک دستور مخرب را رد کند، timeout اعمال کند یا از کاربر برای یک اقدام حساس اجازه بگیرد.

در معماری عامل‌ها، واژهٔ harness همیشه به دقیقاً یک پیاده‌سازی اشاره نمی‌کند. مستندات OpenAI برای Agents API، harness را از **environment** و **application server** جدا می‌کند: harness حلقهٔ مدل و ابزار و نشست را مدیریت می‌کند؛ environment جایی است که کد و فایل‌ها اجرا می‌شوند؛ و application server محصول شما را به این اجزا وصل می‌کند. در معماری‌های دیگر این مسئولیت‌ها ممکن است در یک سرویس یا چند کامپوننت پخش شده باشند.

## حلقهٔ اجرا

هستهٔ سادهٔ بسیاری از Agentها یک loop محدود است:

۱. درخواست و context لازم به مدل داده می‌شود.
۲. مدل پاسخ نهایی می‌دهد یا یک ابزار را پیشنهاد می‌کند.
۳. در این مرحله Harness بررسی می‌کند ابزار و ورودی مجاز و معتبرند یا نه.
۴. ابزار در محیط مشخص اجرا می‌شود و خروجی‌اش ثبت می‌شود.
۵. نتیجه به مدل برمی‌گردد تا تصمیم بگیرد ادامه دهد، اصلاح کند یا متوقف شود.

این loop به خودی خود قابل‌اعتماد نیست. اگر سقف تکرار، زمان، هزینه و حجم خروجی نداشته باشد، می‌تواند بی‌پایان یا بسیار گران شود. اگر مدل بتواند با یک متن ساده «موفق شدم» اعلام کند و سامانه همان را معیار پایان بگیرد، در واقع ادعای مدل را با نتیجهٔ محیط اشتباه گرفته‌ایم.

## اجزای Harness چیست؟

**ابزارها و اجرای آن‌ها.** هر ابزار باید ورودی و خروجی روشن داشته باشد. قبل از اجرا، نوع داده، محدودهٔ دسترسی و اثر جانبی را بررسی کنید. ابزار خواندن فایل با ابزار حذف فایل یک سطح ریسک ندارند. مجوزها باید سمت runtime enforce شوند؛ فقط نوشتن «این کار را نکن» در prompt مرز امنیتی نیست.

**مدیریت context و state.** context همان چیزی است که مدل در یک فراخوانی می‌بیند؛ state وضعیت پایدارتر کار است، مثل فایل‌هایی که تغییر کرده‌اند، کارهای انجام‌شده، تصمیم‌های ثبت‌شده و نتیجهٔ آخرین تست. این دو را یکی نگیریم. لازم نیست کل تاریخچه در هر درخواست تکرار شود، اما اطلاعات مهم باید جایی قابل‌بازیابی بمانند. فایل، پایگاه داده یا ساختار دیگری را بر اساس نیاز انتخاب کنید؛ یک قالب ثابت مثل JSON برای همهٔ پروژه‌ها جواب همیشگی نیست.

**محیط اجرا و محدودیت‌ها.** Agent کدنویسی ممکن است به filesystem و shell نیاز داشته باشد؛ Agent پشتیبانی شاید فقط به CRM و جست‌وجوی پایگاه دانش دسترسی بخواهد. جداسازی workspace، محدودیت شبکه، سقف زمان و دسترسی حداقلی، دامنهٔ خطای مدل را کم می‌کند. اجرای کدی که مدل پیشنهاد داده، بدون sandbox می‌تواند به فایل‌ها یا سرویس‌های واقعی دست بزند.

**بازبینی و توقف.** برای بعضی کارها بررسی خودکار کافی است؛ مثلاً schema یا تست مشخص. برای تغییر بیرونی، انتشار، حذف یا اقدام پرریسک باید تأیید انسانی یا قاعدهٔ صریح داشته باشید. Harness باید راهی برای لغو، rollback یا ارجاع به انسان هم داشته باشد.

**مشاهده‌پذیری و ارزیابی.** trace باید نشان دهد مدل چه contextی دید، چه ابزاری خواست، چه چیزی اجرا شد و محیط چه نتیجه‌ای داد. معیار موفقیت را روی خروجی واقعی بسنجید، نه روی این‌که مدل در پیام آخر گفت کار تمام شده. راهنمای Anthropic دربارهٔ [ارزیابی Agentها](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) هم تأکید می‌کند که transcript و نتیجهٔ نهایی محیط دو چیز جدا هستند.

## چرا Harness روی نتیجه اثر می‌گذارد؟

یک مدل یکسان، با ابزارهای متفاوت، context متفاوت و sandbox متفاوت، دو سیستم متفاوت می‌سازد. اگر ابزارها خروجی بزرگی برگردانند، context زود پر می‌شود. اگر محیط تست نداشته باشد، مدل راهی برای فهمیدن خطا ندارد. اگر state کار پایدار نباشد، یک جلسهٔ تازه ممکن است تصمیم‌های قبلی را گم کند. بنابراین کیفیت Agent فقط خاصیت وزن‌های مدل نیست؛ محصول تعامل مدل با طراحی کل سیستم است.

این به معنی آن نیست که یک Harness ضعیف را با لایه‌های بیشتر درست کنیم. هر قاعده، ابزار، agent فرعی یا مرحلهٔ بررسی خودش هزینه و احتمال خطا دارد. یک گام اضافه را وقتی نگه دارید که در ارزیابی واقعی failure مشخصی را کم کند.

## از کجا شروع کنیم؟

برای اولین نسخه، یک وظیفهٔ محدود انتخاب کنید و پیش از انتخاب framework، مسیر را روی کاغذ بنویسید: ورودی چیست، Agent چه ابزارهایی لازم دارد، چه داده‌ای می‌تواند ببیند، موفقیت چطور بررسی می‌شود و کدام اقدام نیاز به اجازه دارد. بعد traceهای چند اجرای موفق و ناموفق را جمع کنید و از دل خطاها Harness را اصلاح کنید.

اصل **Build to delete** یعنی هر بخش از Harness را برای یک محدودیت واقعی اضافه کنیم، اما دائمی و مقدس ندانیم. با تغییر مدل و runtime دوباره بسنجید که آن مرحله هنوز ارزش هزینه‌اش را دارد یا به سربار تبدیل شده است.

## جمع‌بندی

مدل توانایی پیشنهاد قدم بعدی را می‌دهد؛ Harness دسترسی، اجرا، state، context و ارزیابی آن قدم را مدیریت می‌کند. برای ساخت Agent واقعی، اول یک loop کوچک با دسترسی محدود و معیار پایان قابل‌بررسی بسازید. بعد فقط بر اساس failureهای ثبت‌شده اجزای جدید اضافه کنید. انتخاب مدل مهم است، اما بدون runtime منضبط، ابزار امن و راهی برای دیدن نتیجه، مدل قوی هم می‌تواند فقط سریع‌تر اشتباه کند.
